# Change: 日期時區根因修正 + 標註比對報表版面重新設計

## Why
業主 8/24 回饋（用另外兩份實測檔案：`Taiwan - Semi Portfolio (Tai E).xlsx`、
`(20260824) 大批run TIPO資料.xlsx`）：

1. 日期仍會差一天：8/21 那輪已經「修過一次」的日期解析 bug，這次用業主自己新做的 Excel 檔測試，
   日期還是不對（例如應為 2011/4/25 卻讀成 2011/4/24）。
2. 標註比對報表（8/21 新增的紅字標記匯出）實測後的兩點回饋：
   (1) 新增的比對結果欄位希望插在「被比對欄位的下一欄」，而不是全部附加在檔案最後面
       （例如附件表格裡 D 欄是 Filing Date，希望對應的「申請日比對結果」在 E 欄，而不是被
       丟到很後面的 AL 欄）。
   (2) 除了「正確」／「紅字顯示正確值」，新增第三種情況：TIPO 有查到這筆案號、但該欄位本身
       沒有資料時，顯示紅字「TIPO無資料」。
   (3) 申請案號欄位右邊固定新增一欄，顯示這筆案號有沒有從 TIPO 查到資料：
       「已從TIPO獲取資訊」或「查無資料或非台灣案」。
3. 業主順口問到：如果 Excel 檔裡有多個 table，是不是預設只查第一個？——已確認並回覆
   （見下方「附帶回答」），此問題本身不涉及程式異動，業主表示會先跟同事確認需求後再決定
   要不要處理，本次不動作。

## What Changes

### 1. 日期解析 bug 的根因修正（`lib/parse-upload.ts`）
- 8/21 版的修法（`cellDates:true` + `raw:true`）方向是對的，但 `formatCellDate()` 用
  `getUTC*` 取值的假設是錯的：實測（用業主提供的檔案 + 本專案實際依賴的 `xlsx` 套件版本）
  發現 SheetJS 的 `cellDates:true` 其實是用「執行環境的本地時區」建構 Date 物件（相當於
  `new Date(y,m,d)`，不是 `Date.UTC(y,m,d)`）。在正時區（例如台灣 UTC+8，也是本專案 sandbox
  與多數台灣使用者瀏覽器的時區）下，這會讓建構出來的 Date 物件的 UTC 時間點落在前一天的
  16:00，用 `getUTC*` 取值會誤讀成前一天。
- 修法：`formatCellDate()` 改用**本地時區**的 `getFullYear()/getMonth()/getDate()`
  取值——因為寫入（SheetJS 解析當下）與讀取（`formatCellDate()` 執行當下）都在同一個瀏覽器
  分頁的同一個本地時區下發生，天然互相抵消，結果與使用者電腦的時區設定無關。
- 8/21 版的單元測試用 `Date.UTC(...)` 建構測試輸入，沒有模擬到 SheetJS 的真實行為，因此
  沒測出這個問題；這次改用本地建構子（`new Date(y,m,d)`）模擬 SheetJS 的實際行為，並新增一個
  鎖定「正時區不會誤讀成前一天」的回歸測試。

### 2. 標註比對報表版面重新設計（`lib/excel-annotated.ts`）
- `buildAnnotatedTable()` 簽章新增 `columnMapping` 參數，回傳形狀從「原始欄位 + 附加在最後
  的新欄位」改為單一個「完整標題列 + 完整資料列」（`AnnotatedCell[]`），新欄位在建構時就
  依欄位對應表「插入」在正確位置，不是事後串接。
- 申請案號欄位（`columnMapping.applno`）右邊固定插入一欄「TIPO 查詢狀態」：該筆案號在本次
  查詢結果中找得到就顯示「已從TIPO獲取資訊」，找不到（含格式錯誤、非台灣案、真的查無資料等
  情況）一律顯示「查無資料或非台灣案」。
- 每個「本次選擇比對」的欄位，依 `columnMapping` 對應到的原始欄位 index，插在該欄位右邊，
  不再依 `GREEN_FIELD_DEFS` 固定順序統一附加在最後。
- 比對結果新增第三種情況（原本只有「正確」／「不符（紅字顯示正確值）」兩種）：TIPO 查到
  案件、但該欄位的 `tipoValue` 為空字串時，顯示紅字「TIPO無資料」，與「查無此案號」
  （黑字「查無資料」，屬於案件層級、已經由查詢狀態欄表達）區分開來。

## 附帶回答（不涉及本次程式異動）
業主問：如果 Excel 檔裡有多個 table，是不是預設只查第一個？

**是的，目前只會讀取上傳檔案的「第一個工作表（分頁籤）」**，其餘工作表完全不會被解析或查詢
（`lib/parse-upload.ts` 的 `readRawRows()` 固定取 `workbook.SheetNames[0]`）。用業主提供的
`Taiwan - Semi Portfolio (Tai E).xlsx` 實測確認：這份檔案有 `HG Matters`、`Non-HG Matters`
兩個工作表，目前只會處理 `HG Matters`。
若是「同一個工作表內」有多個表格（例如中間隔了空白列的兩段資料，而不是分頁籤），目前也沒有
偵測表格邊界的邏輯——第一列固定當標題列，其餘所有列都當同一段資料處理，第二個表格的標題列
會被誤當成一筆資料列解析。
業主表示這牽涉到畫面呈現與匯出報表的實際需求，會先跟同事確認使用習慣，本次先不處理，已記錄
於 README 已知限制。
